## 프로젝트 개요

온라인 교육 플랫폼의 수강 신청 흐름을 3단계 폼으로 구현한 프로젝트입니다.

- 1단계: 강의 선택 (카테고리 필터, 개인/단체 신청 유형 선택)
- 2단계: 수강생 정보 입력
- 3단계: 확인 및 제출 (전체 내용 요약, 이용약관 동의, 제출 결과)

단계 간 데이터를 유지하고, 새로고침 후에도 입력 내용을 복구하며, 제출 실패 시 데이터를 보존하고 재시도할 수 있습니다.

## 기술 스택

- 언어: TypeScript
- 프레임워크: Next.js 15 (App Router)
- Mock API: MSW v2
- 테스트: Vitest + React Testing Library
- 유효성 검증: Zod v4
- Style: Tailwind CSS v4

## 실행 방법

```bash
npm install
npm run dev       # 개발 서버 (http://localhost:3000)
npm test          # 테스트 실행 (73개)
npm run build     # 프로덕션 빌드
```

### Mock API 구성

MSW(Mock Service Worker)를 사용합니다. 별도 서버 실행 없이 브라우저와 테스트 환경에서 자동으로 동작합니다.

- **브라우저**: `src/app/layout.tsx`에서 개발 환경일 때 MSW 서비스 워커를 자동 등록
- **테스트**: 각 테스트 파일에서 `msw/node`의 `setupServer`로 인터셉트

Mock 데이터 위치:
```
src/mocks/
├── handlers/
│   ├── courseHandlers.ts       # GET /api/courses
│   └── enrollmentHandlers.ts  # POST /api/enrollments
└── data/
    └── courses.ts              # 12개 강의 (개발/디자인/마케팅/비즈니스)
```

지원하는 에러 시나리오 (POST /api/enrollments):
- `COURSE_FULL` (409): 정원 마감 강의 신청 시
- `DUPLICATE_ENROLLMENT` (409): 이미 신청한 강의 재신청 시
- 500: 서버 오류 (비JSON 응답 포함)

## 요구사항 해석 및 가정

**단체 신청 인원수 해석**

"신청 인원수 (2~10명)"를 참가자 명단 인원으로 해석했습니다. 대표 신청자는 별도이므로 실제 총 인원은 `headCount + 1`명입니다. 확인 화면에 "총 신청 인원: N명 (대표자 포함)"으로 표시합니다.

**개인→단체 전환 시 데이터 처리**

단체 신청으로 필드를 채운 후 개인으로 전환하면 단체 관련 데이터(단체명, 참가자 명단, 담당자 연락처)를 즉시 초기화합니다. 전환 전 확인 다이얼로그를 표시하여 의도치 않은 데이터 손실을 방지합니다.

**참가자 이메일 중복 처리**

참가자 이메일이 대표 신청자 이메일과 동일하면 제출을 차단합니다. 명단 내 참가자 간 이메일 중복도 차단합니다. 두 경우 모두 Zod `superRefine`으로 필드 단위 에러를 부착합니다.

**정원 마감 강의 UX**

`currentEnrollment >= maxCapacity`인 강의는 선택 버튼을 비활성화합니다. 단체 신청 시 남은 좌석이 headCount 상한을 제한합니다(`maxHeadCount = Math.min(10, remaining - 1)`).


## 설계 결정과 이유

### 폼 상태 관리: useReducer + Context, 스텝별 useForm

초기에는 단일 `useForm` 인스턴스를 Context에서 공유하는 방식을 검토했습니다. 그런데 개인/단체 신청처럼 스키마가 런타임에 바뀌는 경우, 단일 인스턴스에서 두 스키마를 교체하면 RHF 내부 상태와 TypeScript 타입 추론이 모두 어긋납니다.

최종 선택은 "각 스텝이 자체 `useForm`을 소유하고, 검증 통과 후 Context(`useReducer`)에 저장"하는 구조입니다. 스텝을 앞뒤로 이동해도 저장된 값을 `defaultValues`로 주입해 입력이 유지됩니다. 스텝별 책임이 명확하게 분리되어 이후 스텝이 추가되더라도 기존 스텝을 건드리지 않아도 됩니다.

### 유효성 검증: "제출 시 한 번"이 아닌 "지금 바로"

검증을 제출 직전에만 하면 사용자는 긴 폼을 끝까지 채운 뒤 처음 필드로 되돌아가야 하는 상황을 겪습니다. 그래서 두 단계로 나눴습니다.

- **필드에서 벗어날 때 (blur)**: 방금 입력한 필드 하나만 즉시 검증합니다. 타이핑 중에 빨간 오류를 보여주는 것은 오히려 방해가 되기 때문입니다.
- **"다음" 버튼 클릭 시**: 현재 스텝 전체를 검증하고, 첫 번째 오류 필드로 자동 스크롤 + 포커스합니다. 사용자가 어디를 고쳐야 하는지 직접 찾지 않아도 됩니다.

### 에러 발생 시 "무엇을 해야 하는가"까지 알려주기

서버 에러를 메시지만 보여주는 것으로 끝내면 사용자는 멈춥니다. 에러 코드마다 다음 행동을 제안하도록 설계했습니다.

- `COURSE_FULL`: "다른 강의 선택하기" 버튼 → 1단계로 이동, 입력 데이터 유지
- `DUPLICATE_ENROLLMENT`: "신청자 정보 확인하기" 버튼 → 2단계로 이동
- `UNKNOWN_ERROR` / 네트워크 장애: 동일 화면에서 재시도 가능, 체크박스 포함 모든 입력 보존

특히 `COURSE_FULL`은 단순 에러가 아니라 다른 강의를 찾아야 한다는 흐름 전환입니다. 버튼 하나로 "에러 상황 → 다음 행동"을 안내합니다.

### 개인 ↔ 단체 전환: 데이터 손실을 사용자가 결정하게

단체 신청으로 참가자 10명을 입력하던 중 실수로 개인 신청 라디오를 클릭했을 때, 자동으로 초기화하면 복구 방법이 없습니다. 그래서 **단체 필드에 입력값이 있을 때만** 확인 다이얼로그를 표시합니다. 아직 아무것도 입력하지 않은 상태에서의 전환은 다이얼로그 없이 즉시 처리합니다.

반대 방향(개인 → 단체)은 추가 필드가 생기는 것이라 데이터 손실이 없으므로 바로 전환합니다.

### 입력 마찰 줄이기

폼이 길수록 사용자가 지칩니다. 몇 가지 작은 장치를 더했습니다.

- **전화번호 자동 하이픈**: `010` 입력 후 숫자를 치면 `010-1234-5678` 형식이 자동 완성됩니다.
- **이메일 도메인 자동완성**: `@g`까지 입력하면 `@gmail.com` 제안이 뜨고, Tab으로 수락하면 커서가 다음 필드로 이동합니다.
- **담당자 연락처 복사**: "신청자 전화번호와 동일" 버튼으로 한 번에 채웁니다.
- **수강 동기 글자수 카운터**: 300자 중 270자를 넘으면 카운터가 주황색으로 바뀝니다. 한계에 가까워지고 있다는 것을 자연스럽게 알립니다.

### Step2 flat type 트레이드오프

React Hook Form은 discriminated union 타입을 직접 지원하지 않습니다. `useForm<IndividualEnrollment | GroupEnrollment>()`으로 선언하면 RHF 내부 타입 추론이 깨집니다.

해결책으로 RHF에 등록하는 타입은 두 유형의 필드를 모두 optional로 합친 flat type(`Step2FormData`)을 사용하고, zodResolver는 실제 `step2Schema`(discriminated union)를 그대로 넘겨 런타임 검증은 정확하게 수행합니다. TypeScript에는 `as Resolver<Step2FormData>`로 캐스팅합니다. 타입 안전성은 스키마 검증 통과 후 Context에 저장할 때 `as Step2Values`로 보장합니다.

### 임시 저장: 실수에 대한 안전망

수강 신청 도중 실수로 탭을 닫거나 새로고침하면 처음부터 다시 해야 합니다. `localStorage`에 스텝 전환마다 저장하고, 다음 방문 시 "이전에 작성하던 신청서가 있습니다" 배너를 표시합니다. 사용자가 이어쓸지 새로 시작할지 직접 선택합니다.

`version` 필드를 함께 저장해 스키마가 바뀌었을 때 구버전 draft를 자동으로 폐기합니다.

## 미구현 / 제약사항

### 이탈 방지 (브라우저 뒤로가기/닫기)

`beforeunload`로 브라우저 닫기/새로고침 감지는 구현했습니다. 다만 Next.js App Router 환경에서 `router.push` 같은 소프트 네비게이션은 `beforeunload`가 발생하지 않아 별도 처리가 필요합니다. 이 부분은 구현하지 못했습니다.

임시 저장이 안전망 역할을 어느 정도 대신합니다. 뒤로가기로 이탈해도 다음 방문 시 복원 배너가 뜹니다.

### 이메일 인증

이메일 형식(정규식) 검증만 구현했습니다. Google OAuth나 이메일 인증 코드 발송은 Mock 환경 범위를 벗어난다고 판단했습니다. 실제 서비스라면 특히 단체 신청에서 참가자 이메일 유효성이 중요해질 것입니다.

### 서버사이드 유효성 검증

클라이언트에서 Zod로 검증하더라도 서버에서 같은 규칙으로 재검증하는 것이 실제 서비스에서 필수입니다. Mock API는 클라이언트 검증을 통과한 요청을 그대로 받는다고 가정했습니다. `INVALID_INPUT` 에러 코드와 `details` 필드 처리는 서버 재검증이 있을 것을 가정하고 클라이언트 쪽만 구현했습니다.

### 반응형 레이아웃 (모바일)

기본 세로 스크롤 레이아웃은 모바일에서도 동작하지만, 참가자 명단 행이 좁은 화면에서 깨지는 문제가 있습니다. 카테고리 필터도 탭이 많을 때 잘릴 수 있습니다. 시간 제약으로 데스크탑 기준 구현에 집중했습니다.
